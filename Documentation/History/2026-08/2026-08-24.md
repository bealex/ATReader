# 2026-08-24 — rows that would not redraw

Three complaints: new chapters never reached the library screen, opening a book reloaded it from
scratch, and the ring on a cover never moved however much was read. The first and the third turned out
to share a cause.

## 1. An `==` that lied

`WorkSummary` and `WorkMetaInfo` both compared by id alone:

```swift
static func == (lhs: Self, rhs: Self) -> Bool { lhs.id == rhs.id }
```

SwiftUI decides whether to re-render a view by comparing the values it stores, field by field, using
each field's own `Equatable` conformance. `WorkRow` stores a `WorkSummary`. So the moment a row was on
screen, every later version of that book compared equal to the one already drawn, and the ring, the
badges and the dates stayed as they were until the row was destroyed for some other reason. The model
was updating the whole time; nothing downstream believed it.

Both types compare every field now. Neither is used as a dictionary key anywhere, so the synthesised
`Hashable` costs nothing that matters, and the change pays for itself elsewhere: the library's
`apply(entries:)` can ask whether anything actually changed before assigning, which under `@Observable`
is the difference between a redraw and nothing.

## 2. A percentage measured against a moving total

Progress was stored as a fraction of the book, meaning the book *as it stood when the reader got
there*, and an ongoing book grows. A reader caught up at 100% stayed at 100% forever: past the read
threshold, so filed under Finished, so excluded from the sweep that looks for new chapters, so never
seen again.

The reading position has no such problem. It names a chapter and a character offset into it, both of
which survive the author publishing. `LocalStore` now re-derives the fraction from the position and the
chapter lengths whenever a position or a table of contents is written, so a book that grows drops back
below the threshold and returns to the Reading shelf on its own.

## 3. Refresh that refreshed the wrong thing

Pull-to-refresh reloaded the shelf. The shelf carries no chapters, so it could never surface a new one;
the per-book counts came only from the daily sweep, which ran from `loadIfNeeded` and so at most once
per launch of the screen.

Worse, `UpdateBadge.write` stamped `lastCheckedAt` on every write, and clearing a book's count is a
write. Opening a book therefore counted as having checked for updates, and a reader who opens a book
most days never got another sweep at all.

The stamp now belongs to a complete pass. A refresh sweeps the books whose `lastUpdateTime` moved since
the device last saw them, which is usually none and never many, and it runs behind the list rather than
under the refresh spinner. The daily pass still walks everything, which is what fills the offline cache.

## What the book page does now

It draws from the store, refreshes behind what is already on screen, writes the answer to the store and
reads it back, assigning each field only where the stored value differs. Reading the copy back is what
keeps the ring honest: `WorkSummary(WorkDetails)` carries the service's idea of progress, which is
nothing this device did, and painting it directly emptied the ring every time the details landed.

"Continue reading" prefers this device's position over `lastChapterId`. The service's figure only moves
when the reader reads on the website, so on a book read here it pointed at whatever chapter they last
opened somewhere else.
