# 2026-10-08

## Where an opening's time went

A book opened onto empty pages, with the text arriving after the cover had finished turning. Timed on
the simulator from the tap, with the bundled book part read:

| | first sheet cut | opening ends |
| --- | --- | --- |
| title page | 38 ms | 884 ms |
| part read, same process | 324 ms | 866 ms |
| part read, fresh process | 1734 ms | 883 ms |

Everything before the chapter's text is in hand takes under 50 ms: building the screen, the store,
the chapter's content. Inside the cutting, for a chapter of 938 paragraphs and 75 pictures:

| | fresh process | same process |
| --- | --- | --- |
| pictures read | 1604 ms | 201 ms |
| text set | 42 ms | 39 ms |
| first paragraph composed | 28 ms | 27 ms |

`ChapterLayout.prepare` read every picture in the chapter before it set a line, because a plate's
depth has to be known to set the line it stands on. Reading meant decoding, shrinking and looking at
every pixel to tell colour art from line work. The same-process figure is high too: the cache held 64
pictures and the chapter has 75, so eleven were read again every time.

Only a picture's size is needed to set a page. `BookImages.prepare(sources:)` now reads that off the
file's header and leaves the pixels until a page that shows the picture is made ready or drawn.

| | first sheet cut, before | after |
| --- | --- | --- |
| part read, same process | 324 ms | 113 ms |
| part read, fresh process | 1734 ms | 138 ms |

A phone is slower than the Mac the simulator runs on, and these weren't taken on one.

## The back of the leaf, blank

Shut before any page was turned, a book showed blank paper on the back of its cover where the page
before should be. `OpeningBook` borrows that page's drawn layer contents, and the contents were
there, but the strips showed nothing. A page that has been on screen, after a turn, was fine. Marking
the layer for display and drawing it again as it's handed over fixes it: the same page shows its
text with the redraw and nothing without it. Why a layer that has only stood at no opacity hands over empty contents wasn't found.

## Driving the reader from a UI test

On the Duo simulator a tap on the reader's close button waited 23 seconds and then landed on the
page, turning it. A drag down the page shuts the book reliably, and `press(forDuration:thenDragTo:
withVelocity:thenHoldForDuration:)` holds it half shut for a screenshot from the host.

## A long chapter with no pictures

A report off the phone put the reader at offset 322,494 of a chapter 460,000 characters and 2,950
paragraphs long, with no pictures in it, and its own log showed 380 ms between asking for that page
and having it. The same chapter and position on the simulator, in a debug build as the phone runs:

| | before | after |
| --- | --- | --- |
| prepared chapter read from the store | 27 ms | 27 ms |
| chapter set as text | 158 ms | 50 ms |
| paragraph ends and soft hyphens found | 68 ms | about 1 ms |
| first paragraph composed | 155 ms | 3 ms |
| page at the position, whole | 400 ms | 70 ms |

Three things, none of them the composing the reader actually wanted:

- **The font was built twice for every paragraph.** `ChapterTextStyle.font` makes a font from a
  descriptor each time it's asked, and both a paragraph's style and its spacing asked. Of the 158 ms,
  103 went there and 38 on building the same attribute dictionary 2,950 times. Appending the text took
  9. The font, the line's depth and the body attributes are made once a chapter now.
- **The chapter was set twice, one after the other.** The composer keeps a copy of the text of its
  own, since an attributed string can't cross threads, and set it the first time a paragraph was asked
  for. It's started beside the layout's own setting now.
- **Two loops asked the string for each character in turn.** Finding paragraph ends and soft hyphens
  is one pass over a copied buffer.

Reading the prepared chapter back is JSON decoding and wasn't touched.

## The prepared chapter as bytes

The prepared chapter was kept as JSON and decoded whole on every opening. For the same 460,000-
character chapter, on the simulator in a debug build:

| | JSON | packed |
| --- | --- | --- |
| size | 2,855,187 bytes | 1,807,865 bytes |
| decode | 23 ms | 8.5 ms |
| encode | 25 ms | 4.5 ms |

What's left of the decoding is mostly making strings: the chapter is held twice, plain and
hyphenated, and both halves are read whether or not the page will use them. Reading only the half the
reader's hyphenation setting asks for should about halve it again, and needs `ChapterContent` to hold its
halves lazily. That wasn't tried.

The book's summary and each chapter's entry in the contents are still JSON. They're small, and a
book with thousands of chapters is where that would start to show.

Every chapter already kept as JSON is packed at the next launch, once, behind the launch
housekeeping. The file's `user_version` goes to 7 when the pass finishes, so one cut short by the app
being closed starts again from whatever is left. A row whose JSON no longer reads is dropped. The
space the JSON took stays in the file as free pages for SQLite to reuse; nothing vacuums it, since a
vacuum holds the store for as long as it runs.
